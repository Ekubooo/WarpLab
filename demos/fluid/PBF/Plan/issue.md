## 未完成

- [ ] [P1｜高] lambda 的寄存器限制与边界路径资源负担（2026-10-23）
  - 当前证据：最新 NCU 为 77 寄存器/线程，256 线程时每 SM 限制为 3 个 block，理论/实际占用率 50.0%/43.1%；每调度器可发射 warp 仅 0.42。前次 NSYS 中约 2.136 ms/帧，占 kernel 时间 34.4%。
  - 方向：独立比较边界查询与纯邻域 lambda 分离。沿用 `volume_Grad`，增加必要的边界密度结果，保持查询位置、公式和执行依赖，计入额外 kernel 与读写成本；也可先检查临时量与资源生命周期。
  - 验收：比较完整压力阶段、整帧均值/P95和数值行为。当前 256 线程模型中，降至 64 寄存器或以下才可支持 4 块；不盲目强制寄存器上限，不承诺占用率变化对应的加速比例。

- [ ] [P1｜高] 连续桶访问与邻域名单间接读取的性能对照（2026-10-23）
  - 问题描述：Unity 对已排序的桶连续遍历，下一位粒子的地址可由下标递增得到；Warp 当前先读 `CacheBuffer[k, i]` 得到邻居编号，再用编号读取位置及其他属性。后者筛掉了无效候选、减少重复查询，但多了一层“先拿编号，才能拿位置”的等待。连续访问与有效名单各有成本，不能仅凭访问形式判定谁更快。
  - 当前依据：此前小规模 NCU 中，lambda/delta/visvor 分别约 56%/73%/50% 的 long-scoreboard 采样落在邻居编号读取后的使用位置。这是访存等待样本的分布，不是整帧时间占比，也不是可直接获得的加速比例。现有邻域缓存已有组合优化收益，不直接回退。
  - 大致方向：先独立尝试提前读取下一位邻居编号，必要时再尝试少量属性预取，检查是否因增加寄存器抵消收益。之后可用同一场景、相同公式和迭代配置，对照直接连续桶遍历，计入候选筛选、缓存构建与读写，以及所有消费 kernel 的总成本。当前 `[邻居槽位, 粒子]` 布局有利于相邻线程读取同一槽位，不因单线程访问不连续就直接转置。
  - 验收：同时比较完整邻域阶段、压力阶段和整帧，保持累加顺序与数值行为；不能只看单个循环或单个 kernel 变快。

- [ ] [P2｜中] Unity/Warp 的实际邻居数量与等工作量对照（2026-10-23）
  - 问题描述：相同粒子总数不等于相同计算量，每个粒子要处理多少邻居也很关键。流体平息后仍会执行邻域循环，而且两边的平滑半径、间距及密度计算配置不同，邻居数不会自动变得一样。用户反馈关闭 VSync 后 Warp 仍约 90 FPS，Unity 约 135 FPS；这是整体帧率差异，尚不能归因于桶访问或邻居数量中的某一项。
  - 当前依据：初始平滑半径/粒子间距之比，Unity 约 1.66，Warp 为 2。按内部均匀分布、达到目标密度的连续近似，邻居数约为 `(目标密度 / 单粒子质量) × 球形支撑体积`；Unity 密度公式等效单粒子质量为 1，对应约 21，Warp 对应约 42。这里是参考估算，Unity 实际运行邻居数尚未采集；此前 Warp 平息状态的缓存平均数约为 42.6（20.5 万粒子）和 46.1（百万粒子），不能把估算与实测混为一谈，也不能因此认定 Warp 邻居数错误。
  - 大致方向：先在两边相同运行阶段统计候选数与有效邻居数的均值、P95 和最大值，分别观察运动中与平息后，并区分内部粒子和自由表面。对照时统一自身是否计入、采样时刻和 3 子步×3 次迭代，核实平滑半径/间距、质量与目标密度的关系；同时记录 Warp 额外的 SDF/体积图、涡度与涡量约束工作。
  - 后续选择：确认数量差异后，再评估支撑半径/间距比例或核函数的取舍，并检查密度误差与流体表现。不能仅为追平 FPS 就减少邻居数，把物理效果变化算成实现优化。当前只记录方向，不修改算法或增加统计代码。

## 附录：lambda kernel 与两个独立小实验

lambda 是压力求解里“**计算每个粒子需要多大修正力度**”的 kernel。它先统计邻居带来的密度与梯度，再加上边界的影响，最后得到 `lambda[i]`；后面的 delta 根据当前粒子和邻居的 lambda，计算实际移动量。

目前它包含两类工作：

- **流体邻域计算**：读邻居编号，再读邻居位置，计算密度和梯度并累加。
- **边界计算**：查询 SDF、法线和体积图，得到边界密度与梯度。

nsys 显示它累计约 **2.136 ms/帧，占所有 kernel 时间的 34.4%**，是最大热点。NCU 又说明它为什么值得继续检查：

| 指标 | 当前值 | 通俗理解 |
|---|---:|---|
| 每线程寄存器 | 77 | 每个线程需要保留较多临时数据，能同时驻留的线程变少 |
| 理论／实际占用率 | 50%／43.1% | 可供调度的线程数量受到限制 |
| 每调度器可发射 warp | 平均 0.42 | 经常没有准备好、可以继续执行的线程组 |
| 访存等待占比 | 73.5% | 很多指令要等前面的数据读取完成；这不是整帧耗时比例 |

可以把它理解成：工人在等材料，而可轮换工作的工人又不够多。

两个独立小实验，分别针对“增加可轮换工作的线程”和“提前准备材料”。

1. **实验一：把 lambda 的边界查询拆出去。**

   当前是：

   ```text
   lambda：邻域计算 + SDF/体积图查询 → 得到 lambda
   delta：读取 lambda 和已缓存的边界梯度
   ```

   实验方案是：

   ```text
   边界查询：得到边界密度、边界梯度
   lambda：邻域计算 + 读取边界结果
   delta：保持现有计算
   ```

   当前 `volume_Grad` 已经缓存了边界梯度，这个实验再保存一份边界密度贡献即可，约增加 **0.82 MB**。

   **它想解决的是寄存器负担。** SDF、体积图查询内部比较复杂，带有不少临时变量和插值操作。拆开后，纯邻域 lambda 可能用更少寄存器，让更多线程同时驻留：一组等待读取时，另一组可以继续计算。

   代价是每帧增加 **9 次 kernel 启动**，并增加结果写入与读取。所以必须比较“边界查询 + lambda”的总耗时，单看 lambda 变快没有意义。它能否降低寄存器、最终是否更快，都需要实测。

2. **实验二：提前读取下一位邻居的数据。**

   现在的主要依赖链类似：

   ```text
   读取邻居编号 → 等待
   读取邻居位置 → 等待
   计算、累加
   再处理下一位邻居
   ```

   可以尝试在处理当前邻居时，提前发起下一位邻居编号的读取：

   ```text
   提前读取下一位编号
   计算当前邻居
   下一轮使用提前读取的编号
   ```

   类似炒当前这道菜时，先让人去取下一道菜的材料。**邻居数量、公式和累加顺序都保持不变，只调整准备数据的时间。**

   这个方向有直接证据：lambda 约 **56% 的访存等待样本**集中在读取邻居编号后的使用位置；delta 对应约 **73%**。说明编号虽已缓存，“先拿编号，才能拿位置”的依赖仍然明显。

   代价是需要额外寄存器保存提前读取的数据，可能反过来降低占用率；编译器也可能已经做了部分提前调度。因此应先少量预取，再检查生成指令和实测耗时。

这两个实验应分别与当前版本对照：**只拆边界、只做提前读取**，各自有效后再考虑组合。继续保持 **3 子步 × 3 次压力迭代**，以完整阶段和整帧耗时判断收益。当前只讨论，不修改代码。

## 附录：lambda 热点与官方开源实现参考（2026-10-23）

本节复查当前 `calc_lambda`、本文件和 `repo.md` 中的两个库，并对照 PhysX 的粒子 CUDA 实现。记录分析与后续实验方向，尚未实施以下实验。

### 1. 当前 lambda 的问题：等数据，同时能轮换执行的线程不够多

| 当前证据 | 通俗理解 |
|---|---|
| 百万粒子 NSYS：lambda 约 **9.51 ms/帧，占 kernel 时间 33.6%** | 仍是最大的单项热点 |
| 此前 20.5 万粒子 NCU：77 寄存器/线程，实际占用率约 43.1% | 每个线程占用较多资源，同时驻留的线程受限 |
| Long Scoreboard 约 73.5% | 很多时候要等读取完成；这是 warp 指令间等待指标，不是整帧时间比例 |
| 约 55.7% 的上述等待样本集中在邻居编号的使用处 | “先取得编号，才能读取位置”的依赖很突出 |

优化重点仍是 **隐藏邻域读取延迟，以及减轻边界查询对 lambda 的资源负担**。百万场景尚未重新采集 NCU，不能直接把小规模的全部硬件指标套过去。

### 2. PhysX：保留邻域名单，但把读取与计算交错安排

是 PhysX 5 系列；此次读取的官方 `main` 版本头标为 **5.12.0**。GPU 模拟源码也已经公开，可以直接查看粒子求解实现。[版本头](https://github.com/NVIDIA-Omniverse/PhysX/blob/b97365c6ddb32fda8469bc788ec18024862b0368/physx/include/foundation/PxPhysicsVersion.h#L25-L27)、[官方开源公告](https://github.com/NVIDIA-Omniverse/PhysX/discussions/384)

它的密度计算中，同样存在“邻居编号 → 邻居位置”的读取关系，但安排成：

```text
开始循环前：准备第一个邻居的位置、第二个邻居的编号

每轮：
    取出已经准备好的当前邻居
    发起下一位邻居的位置读取
    发起再后一位邻居的编号读取
    计算当前邻居的贡献
```

这样，读取下一份材料时，可以继续处理当前材料。**读取总量基本不变，目标是减少连续等待。** 这在 `calculateDensityAndPotential` 和位置修正核中都有直接实现。[PhysX 源码](https://github.com/NVIDIA-Omniverse/PhysX/blob/b97365c6ddb32fda8469bc788ec18024862b0368/physx/source/gpusimulationcontroller/src/CUDA/particlesystem.cu#L2696-L2745)

另外，它通过每轮增加 `numParticles` 访问下一邻居槽位，实质上与当前 **`[邻居槽位, 粒子]` 布局相似**。具体而言，粒子 `i` 的第 `k` 个邻居编号存放在一维数组的 `k * numParticles + i` 处；固定 `i`、令 `k` 加一，地址就增加 `numParticles` 个元素。因此现有布局有成熟实现作为参考，值得先保留。

适合我们的做法是：**先只提前读取编号，再单独比较“编号＋位置”提前读取。** 后者更可能隐藏延迟，也会增加寄存器，必须检查净收益。PhysX 的密度约束公式与当前实现不同，这里借鉴的是读取安排。

### 3. SPlisHSPlasH：边界结果复用已经采用，还能继续研究查询内部复用

它的体积图边界处理会保存边界体积及等效边界位置，后续密度、梯度和位置修正使用这些结果。当前 `volume_Grad` 的 lambda→delta 复用，与这种思路一致。[PBF 实现](https://github.com/InteractiveComputerGraphics/SPlisHSPlasH/blob/master/SPlisHSPlasH/PBF/TimeStepPBF.cpp#L250-L350)

更值得注意的是：它查询距离场和体积场时，**复用同一组插值单元和权重**，避免重复准备查询信息。[边界查询实现](https://github.com/InteractiveComputerGraphics/SPlisHSPlasH/blob/master/SPlisHSPlasH/TimeStep.cpp#L227-L280)

对当前代码有两个方向：

- **小实验：拆出边界查询。** 每轮先得到边界密度和已有的边界梯度，再运行纯邻域 lambda，观察寄存器是否下降。它主要解决资源负担，查询次数不会减少。
- **更后续：共享 SDF/体积图的查询准备过程。** 当前二者是两个独立 NanoVDB Volume，不能直接照搬该库的共享插值方式，需要研究数据组织和底层采样，改动范围更大。

SPlisHSPlasH 这里是 CPU 实现；它证明了结果复用的方法，**不能据此证明拆成两个 GPU kernel 一定更快**。

### 4. 两个参考库还有一种做法：约束为零时，不计算梯度

SPlisHSPlasH 和 PositionBasedDynamics 都会先得到密度约束：

```text
先计算密度，得到 C
若钳制后的 C == 0：
    lambda = 0
否则：
    遍历邻居计算梯度，求 lambda
```

当前 lambda 在同一次循环里，把密度和梯度一起算完；即使最后约束被钳成零，梯度工作也已经发生。[PositionBasedDynamics 实现](https://github.com/InteractiveComputerGraphics/PositionBasedDynamics/blob/master/PositionBasedDynamics/PositionBasedFluids.cpp)

这个方向需要先统计 **`C == 0` 的粒子比例**。如果很多，可能值得尝试；但在 GPU 上拆成两遍会增加邻域读取，并产生分支，未必划算。也不能直接提前退出而漏写 `volume_Grad`。此方向以启用负压钳制为前提，不能将负约束直接当成零。

结合源码证据，建议将实验顺序调整为：

1. **先做邻居编号提前读取**：改动最小，直接对应 NCU 热点，PhysX 有明确先例。
2. **独立做边界查询拆分**：比较完整压力阶段，检查寄存器下降能否抵消额外启动和读写成本。
3. **统计零约束比例**，再决定是否尝试跳过梯度。
4. 更后面研究共享插值准备，以及 128/256 块大小。

每项分别对照当前版本，继续固定 **3 子步 × 3 次迭代**；观察完整阶段耗时、寄存器和等待变化，再决定是否组合。
