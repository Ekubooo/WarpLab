# PBF issues

优先级说明：P0＝阻断；P1＝高；P2＝中；P3＝最低，暂缓处理。

- [ ] [P1｜高] 邻域重复查询与筛选：引入邻域缓存（2026-10-20）
  - 性能问题：`calc_lambda`、`calc_deltaPos`、`calc_curl`、`calc_visvor` 反复执行“查询桶 → 读取候选索引与位置 → 距离筛选”。2026-10-18 的 NSYS 报告中，四核占 CUDA kernel 累计时间约 95.3%，其中压力两核占 74.4%；NCU 显示较多访存依赖等待，平均每条 warp 指令仅约 13/32 个线程活跃。另一固定状态中，每粒子平均约 249 个候选、43 个有效邻居，约 83% 候选被距离检查剔除。
  - 复用方案：同一轮压力迭代内，lambda/delta 可共用有效邻居索引，两核之间位置不变，因此名单有效。2026-10-22 决定：本版先保留每子步构建一次名单、跨压力迭代使用的方式；位置更新后的名单刷新作为最低优先级后续对照，见下方 P3 条目。
  - 速度阶段：`calc_curl` 与 `calc_visvor` 可共用一份有效邻居名单；两核之间位置、速度不变，但必须保持 curl 完成后再执行 visvor，因为后者需要邻居的 curl。`update_position`、`update_velocity` 不遍历邻居，无需缓存。按最终压力位置重新生成名单是后续对照方案，本版沿用压力阶段名单的取舍一并归入下方 P3 条目。
  - 后续比较：当前压力子步内网格与 `pre_New` 查询中心不变，可另行实验每子步只构建一次完整候选索引列表，供多轮压力迭代使用；每轮仍按当前 `pre_Pos` 重新判断距离。不要把“完整候选可复用”误写为“有效邻居可跨迭代直接复用”。跨网格重建或查询中心变化时必须使缓存失效；若要跨位置更新复用有效邻居，需另行设计扩展半径与位移检查。
  - 成本与正确性：先只缓存索引，再独立评估缓存距离、方向、核梯度等几何量。上述固定状态的有效邻居索引约 35 MB（含自身）、完整候选索引约 205 MB，均为量级估算。需要维护计数、索引对应及缓存有效期。2026-10-22 决定：用户已测试极限邻域数量，本版按已测试上限设置固定容量，不实现容量溢出保护，容量不足时直接增大。保留候选顺序有利于控制浮点累加顺序变化。
  - 验收：保持相同配置、相同起始状态与预热条件，比较完整压力阶段、curl/visvor 阶段及无 profiler 的整帧均值/P95；将列表构建、扫描、分配和缓存读写全部计入净成本。检查单轮输出误差、长期密度误差、有限值与边界穿透。当前已初步接入缓存，正确性与性能收益仍待验证；名单刷新对照按下方 P3 条目暂缓。

- [ ] [P2｜中] 压力核寄存器限制：比较线程块大小（2026-10-20）
  - 性能问题：2026-10-18 的 NCU 报告中，lambda/delta 使用 68/67 个寄存器/线程；在 256 threads/block 下受寄存器限制，每 SM 只能驻留 3 个 block，理论 occupancy 为 50%、实际约 45%。delta 每调度器平均仅 0.84 个可发射 warp，约 48% 周期没有可发射 warp，隐藏访存延迟的能力不足。
  - 调整位置：在 `PBF.py` 的 `Example.step()` 中，对对应 `wp.launch(...)` 显式指定 `block_dim=128` 或 `block_dim=256`；本地 Warp 的默认值是 256，`dim=self.n` 保持不变。可为 lambda、delta 分别设置，随后再比较 curl、visvor 的设置。
  - 实验方式：先对原版压力核独立比较 128 与 256，完成各配置的编译、预热后再计时；邻域缓存等其他优化单独验证，再组合较优方案。每组采用独立进程，避免同进程切换配置受下述全局编译期常量绑定问题影响。
  - 验收：以完整压力阶段与整帧耗时为准，同时观察寄存器、occupancy、eligible warps 和访存等待；较小 block 不保证更快，更高 occupancy 也不是单独的成功标准。先保持默认寄存器分配，不同时强制限制寄存器。当前仅记录调参方案，尚无 block size 对照的实测收益。

- [ ] [P3｜最低，暂缓] 有效邻居名单跨位置更新复用的精度与开销对照（2026-10-22）
  - 当前方式：每子步构建一次半径内有效邻居名单，跨压力迭代复用，并继续供 curl/visvor 使用，以节省重复查询、筛选和缓存写入。
  - 待评估问题：压力迭代及碰撞投影会改变粒子位置，可能有原名单外的粒子进入支撑半径；保留旧名单不会自动补入这些邻居。固定网格/完整候选与固定筛选后的有效邻居不同；只重建网格也不会刷新缓存名单。
  - 当前决定：用户接受本版固定名单的计算量与精度取舍，优先级最低，暂不修改实现；后续性能测试若显示刷新成本可接受，再加入。
  - 后续对照：比较当前子步固定名单、每轮压力位置变化后重建名单、最终压力位置更新后为 curl/visvor 重建名单；后两者可分别评估。记录整帧均值/P95、名单构建成本、密度误差和边界穿透，再决定是否采用。

- [ ] [P3｜最低，暂缓] 同进程多实例的全局常量绑定问题（2026-10-20）
  - 触发条件：同一 Python 进程中，先创建并运行一个 `Example`，随后创建另一个实例；常见于自动化测试、批量参数实验、界面内重建或切换场景，以及同时运行多个仿真。
  - 问题：`GRID_id`、`SDF_id`、`VMAP_id` 和配置参数被绑定为模块全局编译期常量。后续实例重新赋值 Python 全局变量，不会自动替换已编译 kernel 中的常量，可能继续查询前一个实例的资源或沿用其配置。
  - 已验证：第二个实例可能查询第一个实例的网格，导致 lambda 错误；先开启负压钳制，再创建关闭钳制的实例，已编译 kernel 仍沿用开启状态。
  - 当前决定：优先级设为最低，暂不处理。当前“每次启动只运行一个固定配置的实例”的主流程可继续使用；`reset_simulation()` 复用原资源，不触发实例重建问题。
  - 后续处理时机与方向：明确需要上述同进程多实例或重建场景时，再考虑将资源句柄保留为实例 kernel 参数，或为不同实例和配置建立独立的 kernel 特化及编译生命周期。
